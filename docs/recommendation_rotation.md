# 추천 목록의 상위 노출 순환

기준: 2026-10-26 현재 구현. 이 문서는 운영 추천 규칙이며 리뷰 기반 가중치 실험과 별개다.

`POST /api/recommend/next`에 적용한다. 카테고리, 선택 장소 중복, 직전 장소 도보 20분과 총 일정 +10분 한도를 먼저 확인한다. 업종별 방문 횟수는 제한하지 않는다. 사용자가 고정한 순서는 변경하지 않는다. 평점·리뷰·가중치는 사용하지 않는다. **노출 순환은 동백전 가맹점(식당·카페·디저트·쇼핑)에만 적용한다 — `category=관광명소`로 조회하면 `rotate()`를 거치지 않고 거리순 그대로 반환한다(`route.py`).** 관광지는 별도 데이터로 관리하며 지역상생형 노출 분산 대상이 아니기 때문이다.

총 여행시간은 경고 기준이다. 설정값은 30~360분을 유지하되, 체류·도보·출발지 복귀를 합한 일정이 설정 시간보다 최대 10분 초과한 경우까지 선택·확정·재계산·메일 링크 재열기를 허용한다. 그보다 초과하면 후보에서 제외하고 재계산을 거절한다. 후보 카드와 전체 요약에 설정 시간 및 초과 시간을 표시한다. 시간 내 후보를 먼저 배치하고, 빈자리를 초과 후보로 채우며 각 그룹 안에서 노출 순환을 적용한다. 자동 코스 초안 API는 기존 시간 내 자동 구성 방식을 유지한다.

기존 가까운 후보 최대 20곳을 대상으로 실제 도보 경로를 확인한다. 시간 내 후보·초과 후보를 따로 정렬하고 시간 내 후보부터 사용한다. 각 그룹에서 마지막 선택 장소(없으면 출발지)와 가장 가까운 후보보다 120초 이내로 더 걸리는 후보끼리 최근 7일 1위 노출 횟수, 전체 목록 노출 횟수, 실제 도보 초, 장소 ID 순으로 정렬한다. 이동 유사 그룹이 작으면 같은 시간 그룹의 나머지 후보를 가까운 순으로 채우고, 시간 내 후보가 부족할 때만 초과 후보를 사용해 최대 3곳을 보여준다. 전체 명부를 대상으로 한 공정성이나 최적 코스를 보장하지 않는다. 최대 20곳의 실제 도보시간을 확인하므로 기존보다 TMAP 호출이 늘어날 수 있다.

## 요청·후보·표시 기록

`POST /api/recommend/next`에서 카테고리가 지정된 추천 요청을 기록합니다. 후보가 0곳인 요청도 저장하며, 카테고리가 없는 단순 코스 재계산은 추천 요청으로 기록하지 않습니다.

| 저장 위치 | 항목 |
|---|---|
| `app_private.exposure_lists` | 요청 ID, 생성 시각, 표시 확인 시각, 배정된 장소 ID 배열, `policy`, `policy_version`, `mode`, `run_id`, `context` |
| `app_private.exposure_candidates` | 요청 ID·장소 ID, 직전 장소에서 도보 초, 기본 체류 분, 복귀 포함 예상 전체 초, 배정 순위, 공통 기대 노출 |

`context`에는 카테고리, 설정 시간, 복귀 선택, 선택한 장소 ID, 도보·초과 제한, 집계 기간, 이동 유사 범위, 후보 검색 한도를 저장합니다. 사용자 ID·이메일·검색어·출발 좌표는 기록하지 않습니다.

- `policy`: `rotation` / `distance` / `legacy`. 현재 공개 화면은 `rotation`만 사용합니다. 거리순 비교 실험의 실행 기능은 아직 구현하지 않았습니다.
- `mode`: `production` / `simulation`. 실험은 `run_id`가 필수이며 운영 요청은 이를 사용하지 않습니다. 현재 순환 집계는 `production`의 표시 확인 기록만 읽으므로 실험 데이터가 운영 순위에 영향을 주지 않습니다.
- `assigned_rank`: 1~3은 배정 순위, 빈값은 적격 후보지만 상위 목록에 배정되지 않은 장소입니다.
- `expected_exposure`: 실제 배정 자리 수 / 해당 요청 적격 후보 수. 후보 4개에 3자리를 배정하면 각 0.75입니다. 정책 비교용 **공통 기준**이며 현재 순위 결정에는 사용하지 않습니다. 구간별 내부 기대값을 구현한 것은 아닙니다.
- 적격 후보는 전체 명부가 아니라 **가까운 최대 20곳 검색 풀에서 실제 경로·여행 조건 검사를 통과한 후보 전체**입니다. 추천 기회 분산 지표도 이 범위로 해석합니다.
- 기존 기록은 `legacy`로 보존하고 당시 후보·기대값은 추정해서 채우지 않습니다. 신규 방식은 `rotation_v1`로 구분합니다.

응답의 `recommendation_id`는 서버가 발급한 목록 ID입니다. 생성 시점의 배정과 사용자 화면 표시는 구분합니다. 프런트엔드는 목록 영역이 화면에 보이고 문서가 활성 상태일 때 `/api/recommend/impressions`로 ID를 보내며 서버는 발급 후 1시간 이내에 한 번만 표시 확인을 기록합니다. 개별 카드가 읽혔거나 실제 방문했다는 뜻은 아닙니다. 표시되지 않은 요청도 후보 분석을 위해 보관하며, 현재 순환에는 최근 7일의 표시 확인 이력만 반영합니다.

`EXPOSURE_DATABASE_URL`이 있으면 Supabase PostgreSQL의 `app_private.exposure_lists`를 사용하며 SSL을 필수로 적용한다. 스키마는 `supabase/exposure.sql`로 미리 생성한다. public/anon/authenticated 접근은 허용하지 않고 Data API도 비활성화했다. 연결 비밀번호는 서버 환경변수에만 보관하며 프런트엔드나 Git에 넣지 않는다. Render에서 URL이 없으면 SQLite로 조용히 전환하지 않고 추천 목록 조회에 503을 반환한다. DB 실패 메시지에 연결 문자열을 포함하지 않는다.

Supabase 프로젝트: `busan-full-course-exposure` (`zidcslicgrjgceszlxfz`), 무료 조직. IPv4 세션 풀러 5432를 사용한다. 최초 생성한 비밀번호는 `python scripts/configure_exposure_db.py`로 터미널에서 입력하여 로컬 .env에 저장한다. 특수문자는 자동 URL 인코딩된다. 로컬 Python은 `python -m pip install -r backend/requirements.txt`로 PostgreSQL 드라이버를 설치해야 한다. Docker 배포는 requirements를 자동 설치한다. 공개 배포는 Render 서버 환경변수 `EXPOSURE_DATABASE_URL` 등록과 해당 코드 배포가 모두 필요하다.

신규 요청·후보·표시 이력을 분석용으로 보관하며, 미표시 요청도 자동 삭제하지 않는다. 순환 계산에는 최근 7일만 반영한다. 로컬 개발에서 URL이 없으면 기존 SQLite `backend/var/exposure.sqlite3`를 사용한다. `EXPOSURE_DB_PATH`로 위치를 바꿀 수 있다. 기존 SQLite 기록은 자동으로 원격 DB로 복사하지 않는다. Supabase 무료 프로젝트는 비활성 기간에 일시 중지될 수 있으므로 발표 전에 상태를 확인한다.

여러 서버가 하나의 PostgreSQL 기록을 공유할 수 있으나 동시 요청은 표시 확인 전 같은 순서를 받을 수 있다. 공개 요청을 반복하는 봇의 인위적 노출 증가를 방어하는 기능은 포함하지 않는다.

검증: 미확인 목록 미집계, 중복 확인 1회 집계, 120초 경계, 7일 집계 범위와 원본 이력 보관, 선택 순서 보존, 복귀 포함 시간 합산, +10분 경계 및 초과 거절, 직전 장소 20분 제한, 별도 프로세스·공개 서버에서 PostgreSQL 저장/재조회. 현재는 노출 집계/순환 구현이며 상생 효과·사용자 만족을 검증한 결과는 아니다. 배포·DB 점검은 [운영 안내](DEPLOYMENT.md)를 따른다.

## 스키마 갱신

서버 전용 로컬 `.env` 연결로 `python scripts/migrate_exposure_db.py`를 실행합니다. `supabase/exposure.sql`은 기존 테이블에 컬럼과 후보 테이블을 추가하는 반복 실행 가능한 변경이며 기존 기록을 삭제하지 않습니다. 두 테이블 모두 RLS를 활성화하고 public/anon/authenticated 접근을 차단합니다. 기존 운영 코드도 계속 쓸 수 있도록 추가 컬럼에 기본값을 둡니다.

로컬 SQLite는 연결 시 기존 테이블을 보완하고 후보 테이블을 생성합니다. 요청과 후보는 같은 트랜잭션으로 저장하며, 잘못된 후보 중복·배정 순위·음수 시간은 거절합니다. 요청 삭제 시 연결된 후보만 함께 삭제됩니다.
